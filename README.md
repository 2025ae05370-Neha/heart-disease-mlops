# Heart Disease Prediction — End-to-End MLOps

Predict the risk of heart disease from patient health data, served as a
cloud-ready, monitored API. This repository demonstrates a full MLOps workflow:
data prep, EDA, model training with experiment tracking, packaging, automated
testing/CI-CD, containerization, deployment, and monitoring.

**Dataset:** [UCI Heart Disease](https://archive.ics.uci.edu/dataset/45/heart+disease)
(Cleveland, Hungarian, Switzerland, VA — 920 records, 13 features, binary target).

---

## Project structure

```

├── requirements.txt          # top-level dependencies (readable)
├── requirements-lock.txt     # exact pinned versions (full reproducibility)
└── README.md
```

## Setup

Requires **Python 3.11+** (developed on 3.13).

```bash
# 1. Create and activate a virtual environment
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate

# 2. Install dependencies
pip install -r requirements.txt    # or: pip install -r requirements-lock.txt (exact)
```

## Quick start with Make (one command)

A `Makefile` automates the whole flow and **auto-detects the platform**
(macOS/Colima vs Linux/native Docker), so the same commands work everywhere
(including the Prayogshala Linux lab):

```bash
make all      # first time: create venv + install deps, then run the full stack
make demo     # afterwards: train + start API + Prometheus + Grafana + traffic
make down     # stop everything
make help     # list all available targets
```

After `make demo`, open:
- API docs — http://localhost:8000/docs
- Prometheus — http://localhost:9090/targets
- Grafana — http://localhost:3000 (admin/admin)

**Kubernetes deployment (Stage 7) in one command:**
```bash
make k8s-demo   # build image, start Minikube, deploy (2 replicas + LoadBalancer)
make k8s-down   # remove the deployment and stop Minikube
```
Then access it: `minikube service heart-disease-api --url` (run in a separate
terminal) and curl the printed URL.

Other useful targets: `make pipeline` (data → train → test), `make test`,
`make lint`, `make mlflow`.

## Reproduce the full pipeline (manual steps)

```bash
# 1. Download the raw dataset (falls back to bundled copies if offline)
python src/download_data.py

# 2. Clean + merge into data/processed/heart.csv
python src/preprocess.py

# 3. (Optional) Explore the data
#    Open notebooks/eda.ipynb in VS Code and select the project venv kernel.

# 4. Train + tune models, log everything to MLflow, save the best model
python src/train.py

# 5. View experiment tracking dashboard
mlflow ui --backend-store-uri "$(pwd)/mlruns" --port 5001
#    then open http://127.0.0.1:5001

# 6. Predict on a sample patient
python src/predict.py
```

## Run the API with Docker

The serving API ([api/main.py](api/main.py)) is packaged in a Docker image.

```bash
# Build the image
docker build -t heart-disease-api:latest .

# Run the container (maps container port 8000 to localhost:8000)
docker run -d -p 8000:8000 --name heart-api heart-disease-api:latest

# Test it
curl http://127.0.0.1:8000/health
curl -X POST http://127.0.0.1:8000/predict \
  -H "Content-Type: application/json" \
  -d '{"age":63,"sex":1,"cp":3,"trestbps":145,"chol":233,"fbs":1,"restecg":0,
       "thalach":150,"exang":0,"oldpeak":2.3,"slope":3,"ca":0,"thal":6}'

# Interactive API docs:  http://127.0.0.1:8000/docs

# Stop and remove
docker rm -f heart-api
```

Example response:
```json
{"prediction": 1, "label": "disease", "probability": 0.5589}
```

> **Apple Silicon note:** the image is Python 3.13 slim. If your container
> runtime emulates x86_64 (e.g. an x86_64 Colima VM), the optimized numpy/scipy
> binaries can crash with SIGILL. Run on a native arm64 engine, e.g.
> `colima start --profile mlops --arch aarch64 --cpu 2 --memory 4` and build with
> `docker --context colima-mlops build -t heart-disease-api:latest .`

### API endpoints

| Method | Path | Description |
|--------|------|-------------|
| GET | `/health` | Health check (used by Docker/Kubernetes) |
| POST | `/predict` | Predict disease risk from patient JSON |
| GET | `/docs` | Interactive Swagger UI |

## Deploy to Kubernetes (Minikube)

Manifests live in [k8s/](k8s): a **Deployment** (2 replicas, health probes,
resource limits) and a **LoadBalancer Service**.

```bash
# 1. Start a local cluster (native arm64 via the docker driver)
minikube start --driver=docker

# 2. Build the image and load it into the cluster
docker build -t heart-disease-api:latest .
minikube image load heart-disease-api:latest

# 3. Deploy
kubectl apply -f k8s/

# 4. Check it is running
kubectl get pods -l app=heart-disease-api
kubectl get svc heart-disease-api
```

### Access the service

Option A — LoadBalancer (run in a separate terminal; needs sudo for port 80):
```bash
minikube tunnel
# then the Service gets an EXTERNAL-IP:
kubectl get svc heart-disease-api
curl http://<EXTERNAL-IP>/health
```

Option B — quick URL (no sudo):
```bash
minikube service heart-disease-api --url
# curl the printed URL, e.g. curl http://127.0.0.1:PORT/health
```

Option C — port-forward (no sudo):
```bash
kubectl port-forward svc/heart-disease-api 9000:80
curl http://127.0.0.1:9000/health
```

### Clean up
```bash
kubectl delete -f k8s/
minikube stop
```

## Monitoring (Prometheus + Grafana)

The API exposes Prometheus metrics at `/metrics`:
- `http_requests_total` — request count by method/endpoint/status
- `http_request_duration_seconds` — request latency histogram
- `heart_predictions_total` — predictions made, by label

A ready-to-run stack (API + Prometheus + Grafana) lives in [monitoring/](monitoring):

```bash
cd monitoring
docker compose up -d --build
```

Then open:

| Service | URL | Notes |
|---------|-----|-------|
| API docs | http://localhost:8000/docs | send some `/predict` requests |
| Prometheus | http://localhost:9090 | Status → Targets should show `up` |
| Grafana | http://localhost:3000 | dashboard **Heart Disease API Monitoring** (login `admin` / `admin`) |

Generate some traffic, then watch the Grafana dashboard update:
```bash
for i in $(seq 1 20); do
  curl -s -X POST http://localhost:8000/predict -H "Content-Type: application/json" \
    -d '{"age":63,"sex":1,"cp":3,"trestbps":145,"chol":233,"fbs":1,"restecg":0,"thalach":150,"exang":0,"oldpeak":2.3,"slope":3,"ca":0,"thal":6}' > /dev/null
done
```

The Grafana datasource and dashboard are **auto-provisioned** (see
`monitoring/grafana/provisioning/`), so no manual setup is needed.

Stop the stack:
```bash
docker compose -f monitoring/docker-compose.yml down
```

## Model

Two classifiers are trained and compared with 5-fold cross-validation and
`GridSearchCV` tuning, evaluated on a held-out 20% test set:

| Model | Accuracy | Precision | Recall | ROC-AUC |
|-------|----------|-----------|--------|---------|
| Logistic Regression | 0.80 | 0.80 | 0.84 | 0.89 |
| **Random Forest (selected)** | **0.82** | **0.82** | **0.85** | **0.91** |

The **Random Forest** is selected (highest ROC-AUC) and saved to
`models/heart_model.joblib`. The saved object is a full scikit-learn
`Pipeline` (missing-value imputation + scaling + one-hot encoding + model), so
the identical preprocessing is applied automatically at prediction time.

### Features used
`age, sex, cp, trestbps, chol, fbs, restecg, thalach, exang, oldpeak, slope, ca, thal`
→ target: `0 = no disease`, `1 = disease`.

## Reproducibility notes

- `requirements-lock.txt` pins exact versions for byte-for-byte reproducible installs.
- `data/processed/heart.csv` is committed so results can be reproduced without
  re-downloading.
- A fixed `random_state=42` is used for splits and the Random Forest.
- Preprocessing lives in a single `Pipeline` saved with the model (no separate
  transformation steps to remember).
